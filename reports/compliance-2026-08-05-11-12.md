## 2. Confirmed violations

**A. Logical Model filename convention — 26 files** (`input/fsh/omop-cdm/5.4/`)
`resource-templates.md` requires `StructureDefinition-<NomDuModeleLogique>.fsh`.
These are named after the OMOP table instead: `Person.fsh` holds
`Logical: OMOPPerson` → should be `StructureDefinition-OMOPPerson.fsh`. Same
for `CareSite.fsh`, `Concept.fsh`, `Measurement.fsh`, … (all 26). The ids
themselves are fine — SUSHI mints `OMOPPerson` from the name, PascalCase as the
Logical Model exception requires (confirmed in
`fsh-generated/resources/StructureDefinition-OMOPPerson.json`). *The script
missed these: its filename check only fires when an explicit `Id:` is
present.*

**B. ValueSet filename mismatch — 1 file**
`input/fsh/omop-cdm/valuesets/ValueSet-Gender.fsh` holds `ValueSet: OMOPGender`
→ expected `ValueSet-OMOPGender.fsh`.

**C. `Id: ehr` contradicts the Logical Model template** —
`input/fsh/ehr/logicals/StructureDefinition-EHR.fsh:12`
The Logical Model entry in `resource-templates.md` is the one exception where
`id` is **PascalCase matching `name`**, not kebab-case. This file has
`Logical: EHR` + `Id: ehr`, while its own filename already assumes the
PascalCase form. Either the id or the filename is wrong; per the standard it's
the id.
⚠️ **This one is not a free fix**: changing it moves the canonical from
`…/StructureDefinition/ehr` to `…/StructureDefinition/EHR`, breaking the
`uses` clause in `input/fml/StructureMap-EHR2FSL.fml:7`. Must be changed
together — and see finding #1 in §4, which touches the same line.

**D. Zero Provenance instances in the entire repo**
`grep -rn "Provenance" input/fsh input/resources` → no matches.
`profile-lifecycle-process.md` Phase 3 step 3 makes this mandatory for every
conformance artifact created or modified, and `terminology-desiderata.md` §11
extends it to CodeSystem/ValueSet/ConceptMap changes. 41 artifacts, 0 history
entries. This is the largest structural gap.

**E. CodeSystem / ValueSet id + suffix conventions — 9 artifacts**
The 4 `Dpi*` CodeSystems, 4 `Dpi*` ValueSets and `OMOPGender` declare no `Id:`,
so SUSHI mints PascalCase ids (`DpiGender`, not `dpi-gender-cs`). Three
distinct deviations:
- ids are PascalCase where the general rule wants kebab-case;
- no `-Cs`/`-Vs` suffix (`resource-templates.md` now applies these **by
  default**, not only on collision);
- `DpiEncounterTypeVS` / `DpiGenderVS` use uppercase `VS`, not `Vs`.

And the collision the suffix rule exists to prevent is already live: **`ValueSet:
DpiModeIn` and `CodeSystem: DpiModeIn` share a name and id**, as do
`DpiModeOut` / `DpiModeOut`. The **FormBuilder exception does not apply** —
these are hand-authored FSH, not FormBuilder output.
`CodeSystem-dm-omop-cdm-v20240229.fsh` is the one that gets the id right
(explicit kebab `Id:`, matching filename); it only lacks the newer `Cs`
suffix.

## 3. Script false positives (do not act on these as written)

- **`StructureDefinition-LogicalBundle.fsh: id 'LogicalBundle' is not
  kebab-case`** — **not a violation.** `resource-templates.md` explicitly
  exempts Logical Models: their id is PascalCase matching `name`. This file
  is compliant. The script applies the kebab rule to `Logical` alongside
  `Profile`/`Extension` without honouring the documented exception.
- **`StructureDefinition-EHR.fsh: filename does not match expected
  'StructureDefinition-ehr.fsh'`** — the finding is real (§2-C) but the
  **suggested fix is backwards**. Don't rename the file to lowercase; fix the
  `Id:` to `EHR`.

No documented exceptions were found: nothing in this repo carries a comment or
Provenance entry justifying a deliberately broken rule.

## 4. Manual review findings

**1. 🔴 Canonical URL drift — every StructureMap points at a base the IG no
longer mints.**
Commit `714e95e` *"(chore): fix canonical URL"* (2026-02-05) changed
`sushi-config.yaml:2` from `https://interop.aphp.fr/ig/fhir/dm` →
`https://aphp.github.io/IG-fhir-dm`. **All 10 `.fml` files were never
updated** — 34 occurrences still reference the old base, plus 3 snippets in
`input/pagecontent/data-platform-transform-layer.md`. Verified against
generated output: `fsh-generated/resources/StructureDefinition-ehr.json`
carries `"url": "https://aphp.github.io/IG-fhir-dm/StructureDefinition/ehr"`,
while `StructureMap-EHR2FSL.fml:7` does
`uses "https://interop.aphp.fr/ig/fhir/dm/StructureDefinition/ehr"`. The
StructureMaps cannot resolve the IG's own logical models. The git history
settles the direction: the FMLs should follow the new canonical, not the
reverse.

**2. `Must Support` — none active, but four dead RuleSets carry it.**
`input/fsh/ruleSets.fsh` defines `CategorySlicingRules` (line 8),
`BundleSlice` (22), `MustSupportOnReference` (28–30), `CreateComponent`
(41–44), all containing `MS`. **None is `insert`ed anywhere in the repo** —
so no `MS` reaches a built artifact, and the repo passes the robustness rule
in practice. Still worth deleting or annotating: unused templates carrying a
forbidden pattern are a trap for the next author.

**3. Robustness principle — not applicable, structurally.**
No `Reference` bound can be narrowed and no cardinality tightened here: the
repo defines no Profiles or Extensions. All 28 StructureDefinitions are
`kind=logical` with `Parent: Base`, declaring their own elements from
scratch.

**4. Trial Use / standards-status — absent.**
No `structuredefinition-standards-status` extension on any artifact; no
`scripts/generate-standards-status.js`, no
`input/data/standards-status.json`. The `derive-standards-status` mechanism
isn't installed. No incidental consumption of Trial Use elements either. Not
a violation — noted so the gap is visible if a maturity badge is ever
wanted.

**5. Documentation completeness — good, with one weak spot.**
The OMOP logical models consistently give every element a short + definition
(`Person.fsh` is representative:
`* person_id 1..1 integer "Person Identifier" "It is assumed that…"`), and
`StructureDefinition-EHR.fsh` has a substantial multi-paragraph
`Description`. Exception: **`LogicalBundle`** has `Title: "LogicalBundle"` —
the raw name, not a human-readable title (`resource-templates.md`: title =
name *with spaces*) — and carries `// TODO add all necessary types` with
only 4 of the 26 OMOP types wired into `entry`.

**6. Example instances — none.**
No `Usage: #example` instance anywhere. The 17 JSON fixtures under
`input/test/map/` are workflow test data, not IG examples, so no artifact
page will render an example. `profile-lifecycle-process.md` Phase 3 step 8
expects at least one conformant example per artifact.

**7. ✅ `path-resource` is correctly wired.** `sushi-config.yaml` lists
`input/fml`, `input/fml/usages/core` and `input/resources/ViewDefinition_OMOP`
— the `build-and-validation.md` gotcha (hand-authored `.fml` invisible to the
build) is already handled here.
